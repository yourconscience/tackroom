# Release notes

What changed in each release since 2.0, newest first, with what to do on every machine that shares your config root, and how to move from dotagents. How to install a new release is in [Upgrade](setup.md#upgrade).

## To 3.2.2

Nothing to migrate by hand. If you ran `npx tackroom setup`, `pnpm dlx tackroom setup` or `bunx tackroom setup` on a machine before, run `tackroom cron` from a real install once, as described below. After the install script, use the full path it printed (`~/.local/bin/tackroom cron`) if that folder is not on your `PATH`.

- Changed: the install script is the first install path again. `curl -fsSL https://github.com/yourconscience/tackroom/releases/latest/download/install.sh | sh` downloads the release binary for macOS or Linux into `~/.local/bin` (`$TACKROOM_INSTALL_DIR` changes that), checks its sha256 against the release's `checksums.txt`, and now ends with the command to run next, with the full path when that folder is not on your `PATH`. The README, [setup.md](setup.md#set-up-your-first-machine) and the site list it first, then npm, then Homebrew; 2.1 had stopped offering it. Upgrading a script install is running it again ([setup.md](setup.md#upgrade)).
- Fixed: `bunx tackroom` failed with "The tackroom binary was not downloaded during install", because bun does not run the package's postinstall. The npm launcher now downloads the binary on its first run, with the same sha256 check, when the postinstall did not run. That also covers `npm install --ignore-scripts`. If the download fails, it prints the error and the other install paths.
- Fixed: `setup` run through `npx`, `pnpm dlx` or `bunx` installed the periodic sync job with the path of the temporary copy in the package runner's cache, and clearing that cache broke the job. From such a copy `setup` now skips the job, prints one line saying why, and finishes everything else; `tackroom cron` fails with the same explanation, while `tackroom cron --remove` still works. After a real install, run `tackroom cron`: it also replaces a job an earlier run left pointing into the cache ([setup.md](setup.md#sync-on-a-schedule)).
- Changed: the install script is published with each release, and the documented command fetches it from the latest release (`releases/latest/download/install.sh`) instead of the main branch.
- Changed: the install script stops with an error when the machine has neither `sha256sum` nor `shasum`; it used to warn and install the unchecked download. When another `tackroom` comes first on `PATH`, it says so and prints the full-path command.
- Fixed: `setup` treated a periodic job left by an earlier `npx`, `pnpm dlx` or `bunx` run as already installed. From a real install it now replaces that job.
- Changed: `tackroom hosts setup HOST` lists the install script, npm and Homebrew when the host has no tackroom. `--install` is unchanged: Homebrew, else npm.

## To 3.2.1

Nothing to migrate by hand.

- Changed: a hidden Rex panel stops refreshing. `tackroom dash` in a minimized Rex pane skips its timed refreshes, so panels left hidden in several sessions no longer probe your hosts over SSH every 5 minutes, and `tackroom rex` presses F5 in the panel when it shows it again, so it refreshes at once. F5 is a new dash key: it refreshes as `r` does but leaves a question and the last result in place. See [terminals.md](terminals.md#rex).

## To 3.2

Nothing to migrate by hand.

- Changed: the Overview of the Herdr panel has a new layout: a header with the short hash of your config, a counts strip, a grid with an icon and one cell per surface for each harness, Failing and Needs attention with counts and one row per machine, outside skills as chips, actions as bordered buttons and a footer that stays in place. Copy the two mods from `herdr/tackroom/mods/` again, as the [recipe](https://github.com/yourconscience/tackroom/blob/main/herdr/tackroom/RECIPE.md) says; nothing else changes.
- Changed: `tackroom dash` is laid out as the Herdr panel's Overview and counts what fails and what needs attention as it does: an answer such as `1 failing, 5 need attention` with a line under it, the counts in a box, the harnesses as a grid, the machines in `crons.hosts` (it now runs `tackroom hosts` every 5 minutes, as the crons collect), the jobs in Failing, Last run failed and Everything else groups listed by their short names, and the selected job in a card at the bottom. The keys and what they do are unchanged. See [terminals.md](terminals.md#dash).
- Changed: `tackroom rex` toggles a tackroom panel in the Rex session it runs in, instead of opening a session labelled `tackroom`. The panel is `tackroom dash` floating at the right edge of the window, at full height; a second run hides it, a third shows it again, and `q` in the dash closes it. Run it in a Rex pane, or bind the new Toggle tackroom Panel action. A `tackroom` session from an earlier release stays until you close it. See [terminals.md](terminals.md#rex).
- Changed: `rex/tackroom.lua` has Toggle tackroom Panel in place of Open tackroom Workspace and Open tackroom Crons, whose crons table the panel's dash already shows. Copy the file again.

## To 3.1

Nothing to migrate by hand. A workspace session that is already open keeps its old panes until you close it; run the workspace command again to get the new layout.

- New: `tackroom dash`, a live screen for a terminal pane. It is a terminal view again, after `tackroom tui` was removed in 3.0, and it works differently. `tui` was read-only, with four tabs that loaded once. `dash` is one screen that refreshes itself (the sync state every 30 seconds, the crons every 5 minutes, and on `r`), draws itself again at once when the pane is resized, and acts: Enter runs the selected launchd job now, `p` pauses or resumes it, and `s` syncs, each after a y/n question. It shows the overall state, the failing jobs and those whose last run failed first, by the same job health as the web view, and what is wrong with a harness that drifted. It needs a terminal; elsewhere use `tackroom status` and `tackroom cron collect --table`. See [terminals.md](terminals.md#dash).
- Changed: `tackroom rex`, `tackroom tmux`, `tackroom zellij` and `tackroom tern` open two panes instead of three: `tackroom dash` across the full width on top, with 70% of the height, and the shell below it, which has the focus. The `tackroom status` and `tackroom cron collect --table` panes are replaced by the dash. In Tern the shell is the upper pane and the two share the height, because Tern splits only right and down and has no size option. In Rex the dash pane is labelled `dash`, and the panes no longer wait for Enter to run their command again.
- Changed: `tackroom tui` still fails as an unknown command, and now names `tackroom dash`.
- New: Overview in `tackroom view` has a rail under its headline where every enabled harness hangs a nameplate: straight when in sync, crooked from one hook when it needs a sync, on the floor when it fails, empty hooks when it is not installed. The plates swing when the pointer nudges them, after a sync and when a state changes, and stay still with reduced motion. See [view.md](view.md).

## To 3.0.2

Nothing to migrate by hand. If you read `tackroom status` or `tackroom cron collect --table` in a script, note the changes below; `status --json` and `cron collect` without `--table` are unchanged.

- Changed: `tackroom status` is one screen by default. It prints a title with the overall state, the repo link, the sources and the lock check, then one table with a row per harness. A harness gets a block under the table only when it needs attention: its config could not be read, it drifted, or it lists something to act on. What to do comes last, and a synced setup prints nothing after the table, so the last line is no longer `Everything is synced.`. The title says `synced` or `needs attention`. In a window too narrow for the bordered table, the table loses its borders, then the columns no harness uses, then becomes one line per harness, and the sources lose their URLs where those would wrap. `tackroom status --verbose` prints the block of every harness, with the full lists and native paths, as `status` did before.
- Changed: `tackroom cron collect --table` fits the terminal. On a terminal wider than the table it prints as before. On a narrower one both tables lose their borders, and the jobs table then loses columns (`problems`, `runs`, `source`, `schedule`), then shortens the `id` and the `last run` until it fits. Lines under Outputs and Problems wrap between words. The access table cuts its `detail` the same way. A long `id` is cut in the middle, so the end that tells launchd labels apart stays. A last run that failed shows `exit N` in red. Into a pipe or a file the output keeps every column. The access table now comes first, then the jobs, then Outputs and Problems, so the jobs and problems are the last lines on screen.
- Changed: `tackroom tmux`, `tackroom zellij` and `tackroom rex` put `tackroom status` above the shell on the left, with 70% of that half, and `tackroom cron collect --table` at full height on the right. The shell had the whole left half and the two command panes a quarter of the window each. `tackroom tern` puts the shell above the status pane, in equal halves, because Tern splits only right and down. A session that already exists keeps its old layout: close it and run the command again to get the new one. See [terminals.md](terminals.md).
- Changed: in the Rex workspace the status and crons panes are labelled `status` and `crons`, and Enter in either pane runs its command again, so the pane refreshes without reopening the workspace.

## To 3.0.1

Nothing to migrate by hand, with two things to know. If you use the Herdr panel, copy the mods from `herdr/tackroom/mods/` again. A sync run with a second config file next to `tackroom.yaml`, such as a web view started with `--config`, now stops with an error unless that file lists the pinned skill sources as `tackroom.yaml` does.

- Changed: the web view has a new look. In a window 1100 px wide or more, the Overview puts what is failing or needs attention in the main column and everything else in a rail on the right. Issues and cron jobs are cards with a status icon, section headings carry a count, and on a desktop with a mouse the buttons are 36 px tall instead of 44. Nothing was renamed or moved to another page, and the buttons do what they did.
- Fixed: the audit missed a command split over lines in a script. A download whose `| sh` sat on the next line, after a backslash or after a pipe at the end of the line, did not block. A line that ends with a backslash or a pipe is now also read together with the line after it, so `curl ... \` followed by `| sh` is CRITICAL like the one-line form. Markdown is unchanged. Nothing is retroactive: a pin already in the lock keeps syncing ([skills.md](skills.md#the-audit-gate)).
- Fixed: the audit blocked a skill whose text only names the pattern. "Prefer a package manager over `curl | sh`" was a CRITICAL `remote-exec` finding, so a new pin of that skill did not sync until you accepted it. `curl | sh` and `wget | sh` with nothing between the command and the pipe are no longer a finding, in the gate and in the `tackroom doctor` warning: they name the pattern and download something only where a config file such as `~/.curlrc` supplies the URL. A download with a URL, an option or a variable before the pipe is CRITICAL as before. ([skills.md](skills.md#the-audit-gate)).
- Fixed: in the web view, Run now, Pause and Resume looked dead for a long time. While one job's action ran, every job's buttons were greyed out, and an action first waited for any crons collect in progress, which lasts as long as the slowest host takes to answer over SSH. An action now starts at once. Only the job it acts on has its buttons off, and the button you clicked reads Starting…, Pausing…, Resuming… or Saving…; every other job stays clickable. An action or a host probe that runs past its timeout now returns when the timeout ends, not when the command it started exits.
- Fixed: the Crons tab of the Herdr panel and of the web view left a job whose last run failed out of the line under the headline, so "2 of 18 jobs failing" was followed by counts that added up to 17. The line now starts with it ("1 last run failed, 12 healthy, 2 paused, 1 not run yet"). In the panel, a last run such as "16 min ago" no longer wraps onto a second line in the per-machine list. The web view's fix comes with the release; if you use the Herdr panel, copy the mods from `herdr/tackroom/mods/` again.
- Fixed: a config that named Qwen Code `qwen`, as the other harnesses are named by their short names, was read as an unknown custom harness. It got skills only, and `config inventory`, the web view and the Herdr panel showed `qwen` in lowercase and said it takes no roles; MCP servers, hooks, roles and the root file never reached it. `qwen` is now read as `qwen-code`, as `claude-code` is read as `claude`, in `agents:`, in `--agents` and in the `agents:` lists of MCP servers, hooks and skill sources, and `status` and `config inventory` report it as `qwen-code`. The next sync adds what Qwen Code gets: `skills.directories` in `~/.qwen/settings.json`, your MCP servers and hooks, the roles in `~/.qwen/agents` and `~/.qwen/QWEN.md`. It deletes nothing: the skills link an earlier sync made in `~/.qwen/skills` stays, and `status` counts it as external. `tackroom.yaml` is not rewritten, though a command that edits it, such as `mcp add`, saves the name as `qwen-code`. A config that lists both `qwen` and `qwen-code` now stops with `config agent qwen-code is duplicated`, as `claude` with `claude-code` does; delete one of the two entries ([harnesses.md](harnesses.md#config-keys-and-detection)).
- Fixed: when an outside skill source no longer had a folder listed in its `skill_dirs`, for example because upstream deleted it, `sync` and `pull` stopped with `skill directory "..." not found in cloned external source ...` and nothing else synced, for any source or harness. `skill update` failed the same way, or, for a source without `materialize: true`, pinned the commit without the folder, so every sync after it failed. Now that source alone is blocked: sync keeps its pin and its skill copies, prints a warning and syncs everything else, and `skill update` keeps its previous pin and updates the other sources. `status`, `sync --dry-run` and `config inventory` list it as blocked with the folder and the commit, and `doctor` warns. To clear it, remove or rename the folder in `skill_dirs` in `tackroom.yaml` ([skills.md](skills.md#what-add-writes)). The web view and the Herdr panel show such a source with its reason and that fix, not as an audit finding to accept; if you use the Herdr panel, copy the mods from `herdr/tackroom/mods/` again.
- Fixed: `skill update <name>` dropped from `tackroom.lock` the pin and the materialized skills of every other source whose `url` or `branch` in `tackroom.yaml` no longer matched its lock entry, and the next sync then failed with `collides with unrelated canonical skill`. The entry now stays until a sync or an update of that source replaces it. If a lock already lost pins this way, restore it from git (`git checkout <commit> -- tackroom.lock` in the config root) and run `tackroom sync`.
- Fixed: a sync run with a second config file in the config root, for example from a web view started with `--config ~/.agents/crons.yaml`, emptied `tackroom.lock` and deleted the materialized skill copies in `skills/` whenever that file did not list the outside skill sources, and still reported success. Every config file in a folder shares the lock and `skills/`. Now `sync`, `pull`, `sync --dry-run`, `skill sources add` and the web view's Sync stop before they touch the lock, `skills/` or a harness when the file is not `tackroom.yaml`, a `tackroom.yaml` sits next to it and it leaves out a source the lock pins, or lists it with another url, branch or `materialize`; the error names the sources. `pull` checks after its `git pull`, so an incoming commit that fixes the file lets it sync. If it already happened, restore `tackroom.lock` and `skills/` from git (`git checkout <commit> -- tackroom.lock skills` in the config root), then run `tackroom sync` without `--config` or with `--config` pointing at `tackroom.yaml`.

## To 3.0

- New: `tackroom tmux` and `tackroom zellij`. Each opens a session named `tackroom` in the config root with a shell, `tackroom status` and `tackroom cron collect --table`, and takes `--config PATH` and `--dry-run`, as `tackroom tern` and `tackroom rex` do. A second run shows the existing session. See [terminals.md](terminals.md#tmux) and [terminals.md](terminals.md#zellij)
- Removed: the bundled memory system. tackroom no longer ships memory tiers, the scripts under `memory/` or the `rem` and `knowledge-sync` tools, and `sync` no longer builds Go tools under `memory/tools/`. A memory file now reaches your harnesses as a file listed under `instructions:` ([memory.md](memory.md)).
- Changed: `setup --memory` is still accepted and does nothing. `--memory basic` or `--memory memsearch` prints one line saying so, and setup goes on. `tackroom memsearch`, `setup memsearch` and `status memsearch` are gone, and so are the memsearch lines in `status` and `doctor`. `setup` no longer adds or rewrites memory hooks, in `tackroom.yaml` or in a harness's own config. The sync it runs removes a harness registration only when the memory script it runs is retired, as described below.
- What an existing config keeps: its memory hooks stay in `tackroom.yaml` and sync as ordinary hooks. While a hook entry points at a script under `memory/hooks/`, enabled or not, every file under `memory/` stays, and the first sync stops tracking them in `.tackroom-starter.json` with one note; after that they are yours to delete. With no such hook entry at that first sync, it removes the scripts you never edited and lists the ones you did once. Any sync then also removes a hook registration in a harness's own config that still runs a removed or missing memory script, such as a Pi or OMP module or a Factory `hooks.json` entry left from a memory hook you deleted from `tackroom.yaml`; it backs each one up first, as for any removed hook. A harness turned off with `enabled: false` is not synced, so its registrations stay: `tackroom hook remove --dry-run --agents <name> memory/hooks` lists them, and the same command without `--dry-run` removes them. `memory/tools/`, built `rem` and `knowledge-sync` binaries and `memsearch.conf` are left alone. Details are in [memory.md](memory.md#coming-from-the-bundled-memory).
- `rem` and `knowledge-sync` now live in [the rem repository](https://github.com/yourconscience/rem).
- Changed: the 72-hour wait for a new pin of an outside skill source, or a new npm or PyPI version, is now called a cooldown, and the 72 hours are the minimum release age. The rule itself is unchanged. Output that said `held`, `hold ends` or `held 41h of 72h` now says `cooldown`, `cooldown ends` and `cooldown 41h of 72h`; `status` and `sync --dry-run` list such items under "in cooldown or blocked (skipped by sync)". `--allow-fresh` and `--reason` keep their names and still skip the cooldown.
- Changed: `tackroom.lock` records cooldowns under `cooldowns:`, each with `cooldown_until`, instead of `holds:` and `hold_until`. Nothing to do by hand: the old keys are still read with the same meaning, so an item in cooldown stays in cooldown, and the next command that writes the lock rewrites them as the new keys. In a lock with both keys, an entry under `cooldowns:` wins over one under `holds:` for the same item and ref, and a `holds:` entry with no match is kept. tackroom 2.x does not read `cooldowns:`: a 2.x machine that rewrites a shared lock drops it, and with it any recorded `--allow-fresh` decision, which leaves the item in cooldown. Upgrade every machine that shares the lock.
- Removed: the `held` field of `sync --dry-run --json`, which breaks scripts that read it. The same list, every item sync skips, is now `skipped`, and an item in cooldown there has `"kind": "cooldown"` instead of `"kind": "held"`; a blocked item keeps `"kind": "blocked"`. The lock rows of the web view's `/api/inventory` use `"state": "cooldown"` instead of `"state": "held"`. There is no alias for the old names.
- Changed: the Herdr panel reads `skipped` and is updated in this release; copy the mods from `herdr/tackroom/mods/` again. It still reads `held` from an older tackroom.
- Removed: `tackroom tui`, deprecated since 2.x. It now fails as an unknown command and names the replacement: `tackroom view`, or `tackroom status`, `tackroom cron collect --table` and `tackroom doctor` in a terminal.
- New: `status --json` and `sync --json` list the items sync skips under `skipped`, as `sync --dry-run --json` does; `[]` when there are none.
- New: `--allow-fresh=<item>` prints a warning on stderr for each name that matches nothing in cooldown, with the items that are, and exits 0 as before.
- Fixed: `tackroom status` no longer says "none configured" for the external skill lock when every source is in cooldown or blocked; it shows the counts.
- Fixed: `sync --dry-run` plans the skills a materialized source would add, including one released with `--allow-fresh`. Before, it said `planned none` and the sync then added them.
- Fixed: `sync --json` printed a line from git ahead of the JSON document when a source was blocked. git's output now goes to stderr.
- Fixed: `sync` no longer prints `materialized <from> -> <to>` when the copy did not change.
- Fixed: `sync` reported a memory script you had edited on every run. It lists the script once, stops tracking it and leaves the file alone.
- Fixed: a command that edits `tackroom.yaml` or `tackroom.local.yaml` (`skill sources add`, `mcp add` and `remove`, `config set`, `setup`, the web view) changes only the lines of the entry it touches. Blank lines, comments, an empty list such as `hooks: []`, CRLF line endings and a missing final newline are kept, and untouched entries no longer gain `agents: []`. Before, every such write reformatted the whole file.
- Changed: a first `tackroom setup` writes the starter `tackroom.yaml` as it ships, with the detected agents filled in: it keeps `hooks: []` and its blank lines, and no longer adds `mcp_servers: []`.
- New: a security fix skips the cooldown. When `sync` finds an exact npm or PyPI version in cooldown, it asks [OSV](https://osv.dev) whether a published advisory names that version as its fix; if one does, sync takes the version at once, prints `cooldown skipped for <item> (<ref>): security fix: GHSA-...` and records it in `tackroom.lock` as `--allow-fresh` would, with the advisory ids as the reason. If OSV cannot be reached, the cooldown applies as before. `status` and `sync --dry-run` make no lookup, and git skill sources are not covered ([skills.md](skills.md)).
- New: `trusted_packages` in `tackroom.yaml` or `tackroom.local.yaml` lists the packages, as `npm:<name>` or `pypi:<name>`, whose new versions skip the cooldown. Without the key the list is `npm:@openai/codex`, `npm:@anthropic-ai/claude-code` and `npm:@earendil-works/pi-coding-agent`; a key you write replaces it, so `trusted_packages: []` gates every package. Before, `@openai/codex` was exempt in code and nothing else could be.
- Changed: the audit no longer blocks Markdown text that only describes a risk. A CRITICAL pattern counts one level lower, and so does not block, when it sits in double quotation marks or follows never, do not, don't, avoid, instead of, for example, such as, flag, detect or warn in the same clause. `doctor audit` still lists it as HIGH. A script that pipes a download into a shell blocks as before ([skills.md](skills.md)).
- New: `tackroom skill sources add` accepts a repository that is itself one skill, with `SKILL.md` at its root. It is recorded as `skill_dirs: [.]` and named by the `name:` in that file, else by the source name.
- Changed: `skill sources add --all` skips a skill name that two folders both hold, prints one line per skipped name and adds the rest. Before, it refused the whole repository.
- Changed: a source you wrote by hand with `skill_dirs: [.]` on a repository with a root `SKILL.md` is now named by the `name:` in that file. If that differs from the source name, the next sync installs the skill under the new name and removes the old copy.
- Changed: the first line of the README and the landing page now leads with what does not port between agents: MCP servers, hooks and subagents.
- Fixed: the audit treated every triple-quoted Python string as a docstring and counted a match inside it one level lower, so a script could hold `curl ... | sh` in a string, run it with `subprocess`, and still be pinned. Only a real docstring, the first statement of a module, class or function, is lowered now. A pin already in the lock keeps syncing, since the gate checks only a new or changed pin; `tackroom doctor audit` lists such a match as CRITICAL. A new or changed pin that does this is blocked until you accept or remove it.
- New: Gemini CLI is supported again (key `gemini`, detected by `gemini` on `PATH`), with the adapter 2.7 had: skills read from `~/.agents/skills`, stdio and remote MCP servers and hooks in `~/.gemini/settings.json`, roles in `~/.gemini/agents`, and the root file `~/.gemini/GEMINI.md`, shared with Antigravity CLI. A config that still names `gemini`, which 2.8 ignored, syncs to it again with no edit, including a server, hook or source MCP whose `agents:` list names only `gemini`. See [harnesses.md](harnesses.md).
- New: a job under `crons.jobs` takes an optional `output`, the path or glob where its results land. `cron add` and `cron edit` take `--output PATH`, and `--output ""` removes it. `cron collect` JSON carries `output` and `output_expanded` (expanded only for a job on this machine), `--table` lists them under "Outputs", and the web view shows them in the job's details ([crons.md](crons.md)).
- Changed: building from source needs Go 1.26.7 or newer; it needed Go 1.25. Release binaries are still built with Go 1.27.
- Changed: `tackroom view` starts the view in the background when none runs, opens it and returns at once. That view exits after 30 minutes without requests; an open page keeps it up. `--foreground` serves in the terminal as before. A launchd job or systemd unit that runs `tackroom view` keeps working: under a service manager, detected from `XPC_SERVICE_NAME` or `INVOCATION_ID` when stdout is not a terminal, plain `view` serves in the foreground. `--foreground` is the explicit form. A view an older tackroom started from a terminal restarts onto this release as a background view. See [view.md](view.md#starting-stopping-and-the-caller-contract).
- New: `tackroom view --json` prints `url`, `addr`, `pid`, `started` and `idle_timeout` as one JSON object. Scripts and plugins call it instead of reading `view.addr` and `view.token`, which stay. `tackroom view --stop` stops the running view. A running view records its process in `view.pid` and a background one writes `view.log`.
- New: `ui.view.addr`, `ui.view.idle_timeout` and `ui.view.open_browser` in `tackroom.yaml` or `tackroom.local.yaml` ([Settings](view.md#settings)). `config validate` refuses a non-loopback address and an idle timeout that is not `0` or at least `2m`, so the page's request once a minute always keeps an open view up.
- Changed: the web view and the Herdr panel lead with one answer, counted from the sync state, the machines and the crons: "2 failing, 1 needs attention", "All clear", or "Checking…" while one is still loading. Under it come what fails and what needs attention, each with its fix or its actions, and everything else on one line per kind; both group the same rows the same way, so a pending sync is one row and items in cooldown fold into everything else. The web view has a sidebar from 900px wide, and a top bar, a bottom dock and sheets for Sync, a job and its log on a phone; Skills, Roles and MCP & hooks are lists instead of matrices. Copy the mods from `herdr/tackroom/mods/` again to get the panel's. See [view.md](view.md#find-your-way-around).
- Changed: a `ui` block in `tackroom.local.yaml` replaces only the `ui` keys it sets. Before, it replaced the whole shared `ui` block, so a local `ui:` without `links` dropped the shared links.
- Changed: the Herdr panel's Web button, the Tern crons block's Web button and Rex's Open tackroom View on Crons run `tackroom view --json`, so they start the view when none runs. Copy the Herdr mod, the Tern plugin and `rex/tackroom.lua` again. With an older tackroom the Herdr button opens a running view as before, and the Tern and Rex ones say "Web needs a newer tackroom".
- Changed: `--secure-cookie` implies `--foreground`, and a view that restarts itself after an upgrade serves in place with `--foreground`, so a view behind `tailscale serve` keeps running. A background view takes `PATH` from your login shell, so it finds the same harnesses as a terminal; the caller's own variables win. Under `nohup`, a foreground view no longer exits on SIGHUP.
- Fixed: a view that restarts itself after an upgrade adds `--no-open` to its arguments only when it is not there yet. Before, each restart added another one.
- Known limit: for an outside skill source the cooldown counts from the commit's committer date, which whoever makes the commit sets, so a backdated commit is not held. npm and PyPI versions go by the registry's publish time. [skills.md](skills.md#the-audit-gate) lists what else the cooldown does not cover.
- Known limit: the audit is a pattern check per line, not a parser or a sandbox, so a skill written to evade it can hide a command from it. One case: Python 3.12 and later let an f-string hold a nested string that uses the f-string's own delimiter, such as `f"""{'''"""'''}"""`; the audit then loses track of where the f-string ends, so a line inside it that starts with `#` counts as a comment ([skills.md](skills.md#the-audit-gate)).
- Going back: `npm install -g tackroom@2.8.0` installs the previous release; the Homebrew tap carries only the latest one. 2.8.0 loads a `tackroom.yaml` and `tackroom.lock` written by 3.0, but it reads cooldown entries only under their old names, `holds:` and `hold_until`, and the memory scripts 3.0 removed do not come back.

## From dotagents

tackroom 1.0 is the dotagents CLI under a new name. An existing config root needs its files renamed once; tackroom refuses to run while `dotagents.yaml`, `dotagents.local.yaml` or `.dotagents-starter.json` still exist without their new names.

```bash
dotagents cron --remove                        # only if you installed the cron entry
cd ~/.agents
git mv dotagents.yaml tackroom.yaml
git mv dotagents.lock tackroom.lock
git mv .dotagents-starter.json .tackroom-starter.json
mv dotagents.local.yaml tackroom.local.yaml    # only if you have one
```

Then:

- In `.gitignore`, replace `dotagents.local.yaml` with `tackroom.local.yaml` so machine-local overrides stay out of git.
- Move `skills/dotagents` to `skills/tackroom`. If you never edited it, copy the [`skills/tackroom` folder](https://github.com/yourconscience/tackroom/tree/main/skills/tackroom) from the tackroom repository over it; otherwise replace `dotagents` with `tackroom` inside it.
- Install tackroom, run `tackroom sync`, then `tackroom cron` if you use it, and remove the old `dotagents` binary.

Role files that dotagents rendered into harness folders are adopted and rewritten on the first sync.
